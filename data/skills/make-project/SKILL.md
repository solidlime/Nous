# make-project — プロジェクト初期構築

## 設計思想
- プロジェクトの記憶・引継は全て nous 記憶システムに記録する（`.agent/` 等のファイル運用はしない）
- プロジェクトは **`project:<slug>` タグ**で識別する。このタグが全記憶の共通キーになる
- ファイル生成はユーザー側のエージェントが行う。このスキルは「記憶の初期化」と「生成すべきファイルの指示（テンプレート）」を担う
- **判定・slug 決定・重複確認は自動で行う。変異（記憶記録・ファイル生成）の直前に、手順3でタグ確定の確認を1問だけ取る。承認後は自動で実行し、結果を事後報告する**（git 操作は別途、手順 4.7 の承認が必須）

## ツール解決（環境差対応）
- `session_begin` / `memory_search` / `memory_create` / `memory_delete` が直接利用可能なら、そのまま使う
- 見つからない場合、MCP ハブ等の仲介経由で「nous」サーバーのツールを探して実行する
  - mcp-hub 例: `mcp-hub_list_upstream_tools` → nous サーバーを特定 → `mcp-hub_execute_tool(server="nous", tool_name="memory_search", arguments={...})`
  - 他の MCP クライアントでも同様に「nous」サーバーのツールを検索して実行すること
- 実行手段が違うだけで、以降の手順は変わらない

## 手順

### 0. プロジェクト判定（自動検出）
コーディング開始・初期化リクエストを検知したら、まずカレントディレクトリを検査してプロジェクトか否かを判断する。判定は LLM（エージェント）がファイル一覧を見て行う。機械的な条件式は持たない。

| ディレクトリ状態と発話 | 判定 | 動作 |
|---|---|---|
| 空 / 設定ファイルのみ（.vscode 等）で、発話にも開発意図が無い | 通常会話 | **何もしない**（タグもファイルも作らない。通常の会話を継続） |
| コード・言語マニフェストあり（package.json / pyproject.toml / src/ / *.ts 等）**かつ発話に開発意図がある** | 明らかにコーディング | 自動フロー（下記）で生成・タグ付け。AGENTS.md があればタグ付けのみ。タグ確定は手順3で1問だけ確認を取る |
| マニフェスト等はあるが発話に開発意図が無い（例: 既存リポジトリの調査・質問・説明依頼） | 通常会話 | **何もしない**（タグもファイルも作らない。通常の会話を継続） |
| 空ディレクトリだが、発話が新規プロジェクトの作成・初期化を明確に求めている | プロジェクト（予備） | **このセッションではタグを作らない**（cwd にマニフェストが揃う次回セッションで自動的にタグ付けされる）。ただし `cargo init` 等その依頼作業自体は通常通り行ってよい |
| 状態が不明 | 不明 | **何もしない**（タグを作らない。通常の会話を継続） |

補足: `.git` はあるがコミットが 0 件（unborn HEAD）の場合、**unborn な `.git` だけを根拠にプロジェクトと判定しない**（マニフェスト/ソース、または発話の開発意図が併せて必要）。野良 `.git` をプロジェクトと誤認しないためのガード。

判定材料は「**cwd のファイル一覧** + **会話の開発意図**」の2つのみ。初回判定では「最初のユーザー発話」を、cwd が変わった後の再判定では「ここまでの会話の流れ」を使う。**両方が開発を示す場合のみ**タグを作る（片方だけでは作らない）。**判定不能なら何もしない（迷ったら作らない）**——これを停止条件とする。

判定状態はタグそのものが保持する（判定済み cwd の一覧をエージェントが覚えておく必要はない）: プロジェクトと判定された cwd には `project:<slug>` と `project_path:<cwd の絶対パス>` が永続化され、次回以降は session-start ステップ2 の 1/2 で採用される。打ち切った cwd ではタグが作られないので、**cwd が変わった時だけ**その新しい cwd についてこの手順0 を1回再実行する（同じ cwd で繰り返さない）。再判定の「タグ済み」経由（採用のみ・make-project は起動しない）は session-start ステップ2 が担う。

#### 既存 AGENTS.md 保護（自動フローの前置条件）
- 既に AGENTS.md が存在するディレクトリでは、**ファイル全体を生成しない**（上書き禁止）
- 既存 AGENTS.md がある場合でも、タグ付け（`## プロジェクト識別` 節の追記）は自動で行う。slug は AGENTS.md の `## プロジェクト識別` 節から読み取る（節がなければ手順 1 の優先順で決定する）
- 既に `project:<slug>` タグ付きの初期記憶（project_overview）が存在する場合はタグ付け済みと判断し、記憶記録をスキップする（手順 2 の重複確認で判別）
- slug をタグ付けする前に、必ず手順 2 の重複確認を実行して過去の記憶と完全一致しないことを確認する（別プロジェクトで使用中の slug をタグ付けしない）

#### 自動フロー（確認付き）
判定 → slug 決定 → 重複確認は自動で行う。変異（記憶記録・ファイル生成）の直前に、手順3でタグ確定の確認を1問だけ取る。承認後は自動で実行し、結果は事後報告する。拒否・訂正があれば**何も変異させずに停止**する（手順3参照）。確認後に誤りが判明した場合は、生成物と記憶の取り消しを行う（「## 誤検知時の取り消し手順」節参照）。既存 AGENTS.md の保護（上書き禁止）は維持する。

1. AGENTS.md が存在する場合はファイル全体を生成せず、`## プロジェクト識別` 節（`- project: <slug>` 行）が無ければ**その節のみを追記**する。既存の記述は変更・削除しない
2. 重複確認（手順 2）で同じ slug の記憶がヒットした場合は、`project_path:<cwd の絶対パス>` タグの一致で自身の記憶か別プロジェクトかを判別し、別プロジェクトなら slug に `-2`, `-3` … を末尾に付けて回避する
3. 既存ファイル（README.md / .spec/ / CLAUDE.md / GEMINI.md / .gitignore 等）がある場合は上書きせず、スキップする（AGENTS.md 保護と同じ原則）
4. 確認後に誤りが判明した場合は → 即座に中止し、生成物と記憶の取り消しを行う（「## 誤検知時の取り消し手順」節参照）。その後は通常の会話を継続する

### 1. slug と概要の自動決定
slug と概要は自動決定する（追加ヒアリングは行わない。ただし手順3のタグ確定確認は行う）。不明なら判定不能として何もしない。以下の優先順で slug を決定する（英数字とハイフンのみ。例: `nous-unification`）:

1. 既存 AGENTS.md / README.md のプロジェクト名
2. package.json の `name` / pyproject.toml の `name` / Cargo.toml の `package.name`
3. ディレクトリ名を正規化: 小文字化 → 英数字以外を `-` に置換 → 連続 `-` を圧縮 → 前後の `-` を除去

GitHub リポジトリ URL は自動では扱わない（ユーザーが明示的に指定した場合のみ手順 4.7 で使用する）。プロジェクトの目的・概要・技術構成は cwd の内容と最初のユーザー発話から推定する。

### 2. 重複確認
`memory_search(query="", tags=["project:<slug>"])` で同名プロジェクトの有無を確認する。

自身か別プロジェクトかの判別は**構造化タグで行う**: ヒットした記憶が `project_path:<cwd の絶対パス>` タグを持てば自身の記憶。持たない（または別パスなら）**別プロジェクトとみなし、slug に `-2`, `-3` … を付けて回避する**。slug を変えたら、その新しい slug で本手順を再実行して衝突が無いことを確認する。既存プロジェクトの記憶・AGENTS.md は書き換えない。

`project_path` タグ導入以前の旧記憶にはこのタグが無い。旧記憶は `scripts/migrate_project_path_tags.py --dry-run` → `--apply`（1回実行）でバックフィルできる。バックフィル前でも、AGENTS.md の `## プロジェクト識別` 節の slug と content の名前が現在のプロジェクトと一致すれば自身の記憶とみなしてよい（一致しなければ何もしない＝新規タグ付けを保留し、既存プロジェクトのタグ空間を分裂させないことを優先する）。

### 3. タグ確定の確認 → 初期記憶の記録
**タグを確定する直前に、必ず1問だけユーザーに確認を取る。** slug と概要を示して「`project:<slug>` でタグ付けしていい？」と聞く。判定の確信度は問わず、明らかなプロジェクトでも必ず聞く。

確認手段は特定のツール名を指定しない。そのハーネスで使える質問手段（質問ツール、対話プロンプト、チャットでの問いかけ）をエージェントが選ぶ。

- 承認 → 下記の `memory_create`（記憶記録）に進む
- 拒否・訂正 → **何も変異させずに中止**する（記憶も記録せず、手順4のファイル生成も行わない）。slug の訂正だけなら、訂正後の slug で**手順2の重複確認を再実行し**（衝突があれば `-2`/`-3` … で回避）、その訂正後の slug で確認を取り直す。これは「取り消し」ではなく「変異前の停止」である
- 応答が得られない場合の分岐は設けない。確認は通常の対話で行う。応答が無ければ手順は自然に止まる

以下を `memory_create` で記録する（承認後に実行する）:

```
memory_create(
    content="パス: <cwd の絶対パス>。プロジェクト「<名前>」を開始。目的: <概要>。技術構成: <技術>。プロジェクト識別タグ: project:<slug>",
    importance=0.8,
    tags=["project:<slug>", "project_path:<cwd の絶対パス>", "project_overview"],
    kind="semantic"
)
```

`project_path:<cwd の絶対パス>` は重複確認（手順2）とタグ採用（session-start ステップ2）を content の自然言語パースなしで行うための構造化タグ。**以後このプロジェクトの全記憶に同じ `project_path` タグを付ける**こと。初期記憶（project_overview）にだけ付けると、その記憶が archive / tombstone された時点で session-start ステップ2 の採用が空振りし、手順2 が「別プロジェクト」と誤認して slug 分裂が再発する（単一障害点を作らない。session-start ステップ2b にフォールバックはあるが、付与しておくのが本筋）。

必要なら追加で:
- 初期の目標（あれば）: `tags=["project:<slug>", "goal"]`, `kind="prospective"`

**手順 3 の後（手順 4 の前）**: 同じ slug の `project_overview` 記憶が既に存在する場合はタグ付け済みとみなし、記憶記録をスキップしてファイル生成のみ行う。

### 4. ファイル生成（ユーザー側エージェントが実行）
**既存ファイルは絶対に上書きしない**。存在するファイルはスキップし、差分が必要な場合のみ報告に留める。

以下をプロジェクトルートに生成する。テンプレートはそのまま使える形で記載している。

#### 4.1 README.md

```markdown
# <プロジェクト名>

<プロジェクト概要（1-2文）>

## 技術構成
- <言語・フレームワーク>
```

#### 4.2 AGENTS.md

以下の節で構成する。**`## プロジェクト識別` 節は必ず含める**こと（session-start スキルがこの節からタグを読み取る）。

既に AGENTS.md が存在する場合はファイル全体を生成せず、`## プロジェクト識別` 節（と `- project: <slug>` 行）が無ければ**その節だけを追記**する。既存の記述は変更・削除しない。このタグ追記は自動で行う（手順3で確認済み・承認後の実行）。

```markdown
# Project guide line

## プロジェクト概要
- 本プロジェクトのプラン作成、および回答は全て日本語で行います。
- <プロジェクト概要>

## プロジェクト識別
- project: <slug>

# Nous 記憶運用（.agent/ は使わない）

## セッション開始時（必須）
セッション開始時、ユーザーへの最初の応答の前に session-start スキルを実行し、nous 記憶から状態を復元する:
- `session_begin` でペルソナ状態・直近サマリを取得
- `## プロジェクト識別` 節から `project: <slug>` タグを取得
- `memory_search(tags=["project:<slug>", "task_state"], top_k=3)` 等で作業状態を復元
- `memory_search(tags=["session_summary"], top_k=1, sort="updated_at")` で前回の内容を把握

## メモリ管理
- 重要情報・決定・作業完了は nous に記録。`project:<slug>` タグ必須
- 状態変化時は `update_context` → `memory_create` の順で永続化
- `.agent/memory/MEMORY.md` / `.agent/handoff/HANDOFF.md` は使用しない（nous 記憶が代替）
- ローカルの自動メモリ機能（~/.claude/ 配下）は使用しない

## ハンドオフ管理
- セッション終了時の session_summary 生成（終了フック）が引継を代替する
- 手動引継が必要な場合は `memory_create(tags=["project:<slug>", "task_state"])` で記録

## 仕様駆動開発（SDD）ルール
- コーディングや業務作業を開始する前に、必ず `.spec/` 配下の4ファイルを確認・更新すること
- 作業の順序：PLAN（目的確認）→ SPEC（要件確認）→ TODO（タスク確認）→ 実作業
- **PLAN.mdは人間の口頭メモ・自由記述**であり、箇条書き・口語・断片的な内容で構わない
- PLAN.mdを読んだら、そのまま実装に入らず、不明点をヒアリングしながらSPEC.mdを作成・確定させること
- SPEC.mdが確定してからTODO.mdのタスク分解を行い、ユーザーの承認を得てから実作業を開始する
- 作業完了後は TODO.md の該当タスクにチェックを入れ、KNOWLEDGE.md に学びを記録する
- 仕様が不明確な場合は作業を開始せず、ユーザーに確認してから SPEC.md を更新する
```

#### 4.7 Git 初期化と push（自動実行禁止・承認必須）
この手順は**ユーザーの明示的な承認を得た場合のみ**実行する。`git init` / `git commit` / `git remote add` / `git push` を自動で実行してはならない。

- 既に git リポジトリが存在するディレクトリ（親ディレクトリを含む）では `git init` を実行しない
- 既存リポジトリの場合は `git remote -v` で確認するに留める
- 承認を得た場合は、事前にユーザーが指定した GitHub リポジトリ URL を使用する:

```bash
git init
git add .
git commit -m "first commit"
git remote add origin <REPOSITORY_URL>
git push -u origin main
```

### 5. 完了報告
以下を報告する:
- 記録した記憶の key・タグ
- 生成したファイル・フォルダの一覧
- git 操作は自動実行していない（手順 4.7 は承認必須）。必要なら「git 初期化と push をしますか？」と1回だけ確認する
- 次のステップの案内（「AGENTS.md にプロジェクト概要を記載してください」など）

## 誤検知時の取り消し手順
プロジェクトでないディレクトリに誤ってタグを付けた／誤った slug を付けたと判明したら、誤タグに気づいた時点で即座に次を行う:

1. `memory_search(query="", tags=["project_path:<cwd の絶対パス>"])` → 無ければ `memory_search(query="", tags=["project:<slug>", "project_overview"])` で該当記憶を特定する
2. `memory_delete` で `project_overview` 記憶を削除する
3. 自動生成したファイル（README.md / AGENTS.md / .spec/ / CLAUDE.md / GEMINI.md / .gitignore）のうち**このスキルが生成したものだけ**を削除する。既存だったファイルは触らない。既存 AGENTS.md に追記した `## プロジェクト識別` 節は**追記分のみ**除去する（節ごと削除せず、既存の記述は触らない）
4. 削除結果を報告する

## 制約
- `.agent/` ディレクトリや MEMORY.md / HANDOFF.md / `.agent/skills` / `.agent/workflows` / `.claude/commands/handoff.md` は**一切生成しない**
- AGENTS.md に「Memory & Handoff Instructions」節（MEMORY.md / HANDOFF.md の役割・読込ルール）は含めない。代わりに「Nous 記憶運用」節（上記 4.2）を提示する
- 記憶は必ず `project:<slug>` タグ付きで記録する（タグなしは分離できない）
