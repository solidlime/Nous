# ADR-002: TTS スタイルアノテーションアーキテクチャ

## Status
Proposed

## Date
2026-07-27

## Context

### 問題
LLM の応答テキストに感情表現（吐息、焦り、興奮など）を埋め込み、TTS に反映したい。
ただし「口調が変わらなくなる」問題（system prompt 依存で毎回同じ表現になる）を避けたい。

### 現状の TTS パイプライン
1. LLM がテキスト生成 → フロントエンドが蓄積
2. フロントエンドが `POST /api/tts/{persona}` を呼び出し
3. バックエンドが `PersonaState.emotion` + `emotion_intensity` を参照
4. caption 構築: `"{emotion}{intensity}%\nPhysical: ...\nMental: ..."`
5. Irodori TTS サーバーに送信（emotion→speed modifier + caption as server prompt）

### 現状の制約
- speed modifier は 3 感情のみ（joy=1.1, sadness=0.9, anger=1.2）
- caption は固定フォーマットで情報量が少ない
- LLM のテキスト内容が TTS の表現に影響しない
- `update_context(emotion=...)` で感情状態は変わるが、音声への反映が限定的

### 検討した案

#### 案A: インラインスタイルタグ方式
LLM が応答テキスト内に `{style:breath}...{/style}` タグを埋め込む。

**棄却理由:**
- メイン LLM の system prompt を複雑化（プロンプト層分離原則に違反）
- 長い応答でのタグ遵守率が 70-80% に低下
- ペルソナの文体指示とタグ指示が競合
- デバッグ困難（プロンプト問題 vs LLM の気まぐれの区別がつかない）

#### 案B: 別途タグ付け用 LLM（ポストプロセッサ）
メイン LLM の応答テキストを、別の軽量 LLM に渡してスタイルタグを付与。

**採用理由:**
- メイン LLM は自然なテキスト生成に集中可能
- タグ付け LLM はスタイル付与に特化（プロンプトがシンプル）
- 口調のバリエーションを制御しやすい
- TTS は already non-streaming なので、レイテンシ増加がチャット応答に影響しない

**懸念点:**
- レイテンシ増加（+0.5-1.5秒）→ TTS 全体に対して 10-20% の増加で許容範囲
- コスト増加（リクエストあたり $0.001-0.005）→ 許容範囲
- 障害点の追加 → フォールバック機構で対応

#### 案C: ハイブリッド（メイン LLM に軽いヒント + ポストプロセッサ）
メイン LLM に軽いヒントを出しつつ、ポストプロセッサで補強。

**棄却理由:**
- 両方の複雑さを合算し、両方の不整合を生む
- メイン LLM がタグを埋め込み、ポストプロセッサが別のタグを追加 → 矛盾解決ロジックが必要
- 複雑さの増加に対して得られるものがない

## Decision

**3層アノテーションアーキテクチャ**を採用する。

```
┌─────────────────────────────────────────────────┐
│  Layer 1: 感情状態（既存）                        │
│  PersonaState.emotion + emotion_intensity        │
│  → 大域的な声色の方向性                           │
├─────────────────────────────────────────────────┤
│  Layer 2: テキスト特徴量ヒューリスティック（新規）  │
│  文長、感嘆符密度、疑問符、反復表現、句読点パターン │
│  → テキスト駆動の動的バリエーション                │
├─────────────────────────────────────────────────┤
│  Layer 3: スタイルアノテーション LLM（新規・任意） │
│  軽量 LLM がテキストを分析しスタイルタグを付与     │
│  → 文脈依存の細かい表現（吐息、間、強調）          │
└─────────────────────────────────────────────────┘
         ↓
   リッチ caption 構築
         ↓
   Irodori TTS サーバー
```

### 各層の詳細

#### Layer 1: 感情状態（既存・拡張）
- 現在の `update_context(emotion=...)` を維持
- speed modifier のマッピングを拡充: `surprise=1.15`, `disgust=0.95`, `fear=1.2`, `neutral=1.0`
- caption に `emotion_intensity` をより反映させる

#### Layer 2: テキスト特徴量ヒューリスティック（新規・ルールベース）
```python
def analyze_text_features(text: str) -> dict:
    return {
        "avg_sentence_length": ...,  # 短い文が多い → 焦り/興奮
        "exclamation_density": ...,  # 感嘆符密度 → 興奮度
        "question_ratio": ...,       # 疑問符比率 → 困惑/問いかけ
        "ellipsis_count": ...,       # 「…」の数 → 間・ためらい
        "repetition_detected": ...,  # 反復表現 → 強調/感情高ぶり
    }
```
- 決定論的で、レイテンシがほぼゼロ、LLM に依存しない
- 同じ感情状態でも、テキスト内容が違えば異なるアノテーションを生成

#### Layer 3: スタイルアノテーション LLM（新規・オプション）
- `emotion_intensity >= 0.6` の場合のみ起動（コスト最適化）
- GPT-4o-mini または Claude Haiku を使用
- プロンプトは 200 トークン程度の固定テンプレ + テキスト本体
- 出力は `{style:breath}`, `{style:pause}`, `{style:emphasis}` の3種類に限定
- **フォールバック**: LLM 呼び出し失敗時は Layer 1+2 のみで続行

### なぜ「口調固定化」問題を解決するか
1. **Layer 1 は動的**: `update_context` で感情が会話ごとに変わる
2. **Layer 2 はテキスト駆動**: 同じ感情でも、テキスト内容が違えば違うアノテーションになる
3. **Layer 3 は文脈依存**: LLM がテキストの意味を理解してスタイルを判断
4. **3層の組み合わせ**: 同一の感情状態でも、異なるテキストに対して異なる出力が得られる

## Alternatives Considered

### 案A: インラインスタイルタグ方式
上記「棄却理由」参照。

### 案C: ハイブリッド
上記「棄却理由」参照。

### ルールベースのみ（LLM なし）
- Pros: 最速、決定論的、コストゼロ
- Cons: ニュアンスに欠ける、複雑な感情表現は不可能、メンテナンスコストが高い
- 棄却: Layer 2 として採用したが、Layer 3 の補強が必要

## Consequences

### ポジティブ
- メイン LLM の system prompt を汚染しない（プロンプト層分離原則の維持）
- 動的バリエーションにより「毎回同じ口調」問題を回避
- Layer 3 はオプションなので、段階的に導入可能
- 既存の `voice_emotion_link`、emotion update 機構と整合

### ネガティブ
- Layer 3 追加によるレイテンシ増加（+0.5-1.5秒）→ TTS 全体に対して 10-20%
- Layer 3 のコスト増加（リクエストあたり $0.001-0.005）
- 障害点の追加 → フォールバック機構で対応必要

### リスク
- Irodori TTS がスタイルタグ/リッチ caption を正しく解釈するか不明 → P0-P2 実装後に検証必要
- Layer 2 のヒューリスティックが不適切なアノテーションを生成する可能性 → チューニング必要

## Implementation Plan

| 優先度 | 実装内容 | 工数 | 効果 |
|--------|---------|------|------|
| P0 | speed modifier マッピング拡充 | 0.5日 | 低（3→6感情） |
| P1 | Layer 2: テキスト特徴量ヒューリスティック | 1-2日 | 中（動的バリエーション） |
| P2 | caption フォーマットのリッチ化 | 1日 | 中（Irodori への情報量増加） |
| P3 | Layer 3: スタイルアノテーション LLM | 2-3日 | 高（文脈依存表現） |

**P0-P2 まで実装して Irodori の反応を確認してから、P3 の要否を判断すべき。**
