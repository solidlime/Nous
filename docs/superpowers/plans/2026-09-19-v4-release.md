## 0. リリース判断

| 判断 | 内容 |
|------|------|
| バージョン | 4.0.0（契約統一・get_context 純粋化・設定キー削除の破壊的変更を含む） |
| 互換戦略（破壊的変更の全対象） | ① envelope（`{"success":...}` / 平文 Error → `{ok, data, error:{code,message}}`）② get_context の副作用分離（session_start 副作用を `session_begin` へ）③ H4 設定キー削除 ④ memory_search 重み引数のプリセット化。すべて v4.x で warning ログつき併存、HTTP は `?compat=legacy` で旧形式選択可、v5 で削除 |

| 実行時生成禁止 | 契約の生成は実行時には行わない（配布・デバッグを難しくするため） |
| C1 の実装方式（計画改訂3・#003 設計判定） | **生成をやめ、`nous/domain/tools/registry.py` を宣言の単一情報源とし、3 面の生きたスキーマを registry と突合する常設パリティテスト（`tests/parity/test_tool_contract_registry.py`）で強制する**方式を採用。理由: 生成器は面固有ロジック（envelope ラップ・組込 DSL 写像・alias）を写し取る必要があり、さらに**意図的な非対称を黙って正規化してしまう**（意図的乖離は registry の `divergence` に理由を書かせ、テストが空文字を許さない）。生成物のコミットと CI ドリフト検出という当初の狙い（乖離の機械検出）は、テストが同等以上に達成する |

## 2. フェーズ構成（依存順・P3→P4 は直列）

### P0: 基盤計測とガードレール（~0.5 日）
| 項目 | 内容 |

| 項目 | 内容 |
|------|------|
| 単一 DSL（C1） | `nous/domain/tools/registry.py` にツール定義を宣言（MCP 14 + 組込 12 の全件、面ごとの引数契約と意図的乖離の理由つき）→ `tests/parity/test_tool_contract_registry.py` が 3 面の**生きた**スキーマ（`TOOL_DISPATCH`・`register_tools` の実シグネチャ・`MEMORY_TOOLS` の input_schema・HTTP 実行可能集合）と registry を双方向に突合。ドリフト注入試験で検出能力を確認済み（計画改訂3: 生成は採用せず） |
